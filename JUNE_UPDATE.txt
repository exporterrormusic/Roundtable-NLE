PART I — STRUCTURAL ISSUES & GENERAL PROBLEMS
================================================================================

── 1.1  CRASH EPIDEMIC (ACCESS_VIOLATION DOMINANCE) ──────────────────────

  The crash log on May 11, 2026 recorded 540+ crashes in a single day.
  Across ~3 weeks, 97.6% of all crashes (403 of 413) were ACCESS_VIOLATION.
  The crash_log.txt shows the app was restarted ~38 times on May 26–27 alone,
  with 3 explicit std::terminate calls.

  Root patterns identified in prior analysis:
    a) Widget paint recursion — paint → layout → repaint loops across the
       entire dock widget tree. A thread_local guard was added to
       TimelinePanel but the crashes continue. This accounts for ~197
       paintSiblingsRecursive frames in stack traces.

    b) GPU pipeline crashes (nvoglv64.dll) — TDR from mutex contention,
       device-lost, stale GPU handles. 69 primary crashes in the driver.

    c) Use-after-free in signal/slot delivery — widgets accessed after
       destruction. Despite a comprehensive m_destroying guard campaign
       across 22+ classes, the problem persists.

    d) The crash handler itself may be re-faulting, causing infinite crash
       loops that produce zero-length minidumps.

  STATUS: The thread-model fix (May 12) replaced try_to_lock with blocking
  lock in CompositeService, and the GpuScheduler (Unreleased changelog)
  centralized vkQueueSubmit. These helped but did not eliminate the root
  causes. The HEAP CORRUPTION (0xC0000374) crash in the presenter path
  remains undiagnosed — AppVerif was recommended but the investigation
  appears incomplete.

  RECOMMENDATION: This is the #1 priority. A stable NLE cannot ship with
  these crash rates. Run setup_appverif.ps1 and systematically root-cause
  the remaining ACCESS_VIOLATIONs. The paint recursion alone suggests a
  deeper layout management issue in the dock widget system.

── 1.3  THREE INCOHERENT CACHE SYSTEMS ──────────────────────────────────

  The codebase has three independent caches with no shared eviction policy:

    a) FrameCache (CPU RAM ring buffer) — entry-count capped
    b) GpuTextureCache (VRAM texture cache) — entry-count + byte capped
    c) CompositeService internal LRU — for composited frames

  Each cache makes independent eviction decisions. The GpuTextureCache can
  evict a texture that CompositeService still references. FrameCache can
  hold CPU-side pixels that GpuTextureCache already evicted, creating
  redundant decode work. CacheCoordinator was added as a step toward
  unification but it coordinates via callbacks, not a unified policy.

  This is documented in the GPU Memory Analysis (May 13, 2026) and the
  Render Graph Plan Phase E (Unified Cache — NOT STARTED).

  RECOMMENDATION: A single UnifiedCacheManager should own all eviction
  decisions. Pin textures referenced by in-flight command buffers using
  the existing pin/unpin infrastructure (already partially implemented).

── 1.4  UNDO SYSTEM INCONSISTENCIES ─────────────────────────────────────

  The undo system analysis (repo memory) identified 5 specific issues:

    a) PropertiesPanel double-signal: Both valueCommitted AND editingFinished
       connect to applyTransform(), creating TWO undo entries for keyboard
       input.

    b) PropertiesPanel uses execute() instead of pushWithoutExecute() —
       values are already applied by applyTransformLive() but execute()
       re-applies them, risking double-keyframe creation.

    c) PropertiesPanel always writes keyframes at time 0, ignoring the
       playhead position. EffectControlsPanel correctly uses clip-relative
       tick time.

    d) PropertiesPanel doesn't detect whether a keyframe was created vs.
       updated during scrub, making undo less precise.

    e) Effect parameter handling and transform handling use different
       undo patterns (pushWithoutExecute vs execute) inconsistently.

  RECOMMENDATION: These are moderate-severity, well-documented bugs. Fixing
  them would be a focused 1-2 day effort with high user-visible impact.

── 1.5  TRIM OPERATIONS IGNORE MULTI-SELECTION ──────────────────────────

  Critical bug: ClipTrimHead and ClipTrimTail operate on only the clicked
  clip (m_dragClipRef), completely ignoring m_selection. In Premiere Pro,
  trimming one selected clip trims all selected clips together.

  ClipMove correctly handles multi-selection by populating
  m_dragSelectedClips, but trim modes never do. The trim functions
  (EditOperations::trimClip, EditOperationsTrim.cpp) only accept a single
  clipId — there is no multi-clip trim variant.

  RECOMMENDATION: Add a multi-clip variant of trimClip() and wire it into
  the ClipTrimHead/ClipTrimTail drag handlers.

── 1.6  FILE WATCHING GAPS ───────────────────────────────────────────────

  TimelineWorkspaceIntegration.cpp watches media files referenced by
  timeline clips, but:

    a) Project Bin assets are NOT watched. Files replaced on disk while
       sitting in the bin show stale thumbnails until app restart.

    b) ThumbnailGenerator cache keys by path only, not by mtime. Even if
       watching were added, the cache would still return stale data.

    c) Source Monitor for orphaned clips (not on any timeline) is not
       watched.

  RECOMMENDATION: Extend QFileSystemWatcher to bin assets, add mtime-based
  cache invalidation to ThumbnailGenerator.

── 1.7  SPINE LICENSING & AGPL COMPATIBILITY ────────────────────────────

  Documented in CHANGELOG "Known Issues":
    - spine-cpp ships under the Spine Runtimes License, requiring every
      end user to hold their own Spine Editor license.
    - AGPL-3.0 §10 requires linked dependencies to be AGPL-compatible.
      Resolution is pending.

  STATUS: Blocker for public release. No clear resolution documented.

── 1.8  BUILD SYSTEM COMPLEXITY ─────────────────────────────────────────

  The project requires a specific cmake version (3.31.6, project-local at
  tools/cmake/) because the system cmake (conda) interferes. Unity builds
  are gated behind a flag. LTO is gated behind ROUNDTABLE_LTO. The setup
  process requires setup.bat → build.bat → launch.bat.

  The project also has 7 identical "Build" tasks registered in tasks.json
  (duplicates), suggesting configuration drift.

  RECOMMENDATION: Clean up duplicate tasks. Consider a single build.ps1
  that auto-detects the correct cmake. Add a pre-commit hook or CI check
  for cmake version.

── 1.9  INCOMPLETE RENDER GRAPH MIGRATION ───────────────────────────────

  Render Graph Phases A-C (data structures, DAG dispatcher, pass porting)
  are complete and the feature flag (s_useRenderGraph) is toggled on.
  However:

    - Phase D (fault isolation) — NOT STARTED
    - Phase E (unified cache) — NOT STARTED
    - Phase F (telemetry) — NOT STARTED

  The graph-computed barriers are disabled; renderers manage their own.
  A global transfer→compute barrier is inserted for safety.

  RECOMMENDATION: Complete Phases D-F. The render graph is the right
  architecture but the half-finished state means it's not delivering its
  full benefit (automatic barrier derivation, resource lifetime tracking).

── 1.10 MISSING TEST COVERAGE IN CRITICAL AREAS ──────────────────────────

  The test suite has ~37 test files covering timeline, audio, compositor,
  effects, export, etc. However:

    a) No test for multi-selection trim (the known bug above)
    b) No test for paint/layout recursion guards
    c) No test for crash recovery flow
    d) No test for file watching / asset refresh
    e) No GPU pipeline integration tests (tests are CPU-only)
    f) No fuzz tests for project file deserialization

  RECOMMENDATION: Add tests for the known bug areas. GPU pipeline testing
  would require a headless Vulkan device, but the render graph at least
  can be tested for graph correctness without a GPU.

PART II — PERFORMANCE & STABILITY IMPROVEMENTS (LOW OVERHEAD)
================================================================================

── 2.1  ADD GPU DEVICE-LOST RECOVERY ─────────────────────────────────────

  Currently, a GPU device loss (TDR, driver crash, GPU hang) is fatal.
  The app has no recovery path. DaVinci Resolve and Premiere Pro both
  survive GPU resets by rebuilding the Vulkan/D3D device and re-uploading
  all resources.

  IMPLEMENTATION: On VK_ERROR_DEVICE_LOST, catch the error in
  GpuWorkSubmission, call a recovery callback that:
    1. Destroys all Vulkan resources
    2. Creates a new VkDevice
    3. Re-uploads all GPU-resident textures/caches
    4. Recreates the swapchain
  This is the single highest-impact stability fix available.

── 2.2  FIX PAINT RECURSION AT SOURCE ────────────────────────────────────

  The thread_local guard is a band-aid. The real fix requires identifying
  WHY layout changes trigger repaints that trigger layout changes. Common
  causes in Qt:

    a) setGeometry() called inside paintEvent()
    b) update()/repaint() called inside resizeEvent()
    c) Style sheet changes triggering recursive layout invalidation
    d) QSplitter resize loops in dock widget hierarchies

  RECOMMENDATION: Audit every paintEvent(), resizeEvent(), and
  update()/repaint() call in TimelinePanel and DockBehavior. Add
  QElapsedTimer-based recursion detection that logs the exact call chain
  (not just a thread_local bool that silently aborts).

── 2.3  DECOUPLE AUDIO CLOCK FROM GPU COMPOSITING ────────────────────────

  Currently, AVSyncClock (audio) and FrameClock (video) are tightly
  coupled. If the GPU compositor stalls, the audio clock keeps ticking,
  causing A/V desync. The PlaybackController should use a single unified
  clock with backpressure — if the compositor is behind, the clock should
  not advance.

  This was identified in the May 11 stability analysis as recommendation #6.

── 2.4  ADD FRAME DROP METRICS & ADAPTIVE QUALITY ────────────────────────

  The app has no frame-drop counter or adaptive quality scaling. When the
  GPU can't keep up, frames are silently dropped with no user feedback.
  Professional NLEs show a "dropped frame" indicator and optionally reduce
  playback resolution (Full → 1/2 → 1/4) to maintain real-time playback.

  IMPLEMENTATION: Add a dropped-frame counter to FrameClock. When drops
  exceed a threshold, automatically reduce the Program Monitor's render
  resolution. Show a green/yellow/red indicator in the transport bar.

── 2.5  AUDIOSYNC populateCards() OPTIMIZATION ──────────────────────────

  Already partially addressed (repo memory: audio-sync-clear-matches-bug,
  audiosync-multi-session-persistence-fix), but populateCards() still
  destroys and recreates ALL card widgets on every refresh. For large
  scripts with hundreds of lines, this is the #1 UI bottleneck during
  project open.

  RECOMMENDATION: Implement widget recycling — reuse existing card widgets
  and only update their content, rather than full destroy+create cycles.
  The O(N×M) → O(N+M) transcription fix was a good start; widget recycling
  is the logical next step.

── 2.6  BATCH GPU COMMAND SUBMISSION ────────────────────────────────────

  GpuScheduler already centralized vkQueueSubmit, but each composite frame
  still submits independently. Batching 2-3 frames into a single submit
  (where latency allows) reduces driver overhead.

  IMPLEMENTATION: Add a submission batching window (~2-3ms) where the
  scheduler collects work before submitting. This is how Vulkan best
  practices recommend reducing CPU-side driver overhead.

── 2.7  LAZY SHADER COMPILATION ──────────────────────────────────────────

  All 45+ GLSL compute shaders are compiled to SPIR-V at build time.
  However, all shader modules are loaded at startup. On first launch,
  creating 45+ VkShaderModules can take 1-2 seconds.

  RECOMMENDATION: Defer shader module creation to first use. Cache
  VkPipeline objects. Use VK_EXT_pipeline_creation_cache_control for
  faster subsequent launches (persist the pipeline cache to disk).

── 2.8  MOVE PREWARM OFF THE UI THREAD ────────────────────────────────────

  The May 11 stability analysis identified prewarmPlaybackResources as
  a source of UI-thread stalls. The May 12 thread-model fix addressed this
  partially by giving prewarm its own mutex (m_openMediaHandlesMutex), but
  the prewarm work itself should be fully async with no UI-thread blocking.

  RECOMMENDATION: Verify no remaining synchronous prewarm calls on the UI
  thread. All prewarm should use the dedicated prewarm thread.

── 2.9  THUMBNAIL GENERATION CACHING ─────────────────────────────────────

  ThumbnailGenerator caches by {canonicalPath, maxWidth} but has no mtime
  check. When a file is overwritten, stale thumbnails persist. Adding an
  mtime to the cache key is trivial and prevents confusing stale previews.

── 2.10 CRASH LOG DEDUPLICATION ──────────────────────────────────────────

  The crash log appends every crash, including rapid crash loops. The
  May 12 cleanup trimmed from 9472 lines to 540 lines manually. An
  automated deduplication system (group identical stack traces, only log
  the first N occurrences per session) would keep logs manageable.

── 2.11 REMOVE REMAINING try_to_lock PATTERNS ────────────────────────────

  The 2026-05-12 audit found try_to_lock still present in
  CompositeServiceFrame.cpp (lines 109, 650). The thread-model fix
  replaced the main compositeFrame lock with blocking unique_lock, but
  these two remaining try_to_lock calls are correctness issues:
  if the lock is contended, they silently skip work rather than waiting,
  potentially causing dropped frames or A/V desync.

PART III — MAJOR LONG-TERM CHANGES FOR A PROFESSIONAL NLE
================================================================================

── 3.1  UNIFIED RENDER GRAPH WITH AUTOMATIC RESOURCE MANAGEMENT ──────────

  The current render graph (Phase A-C) is a good start but is essentially
  a DAG dispatcher with manual barrier management. A production render
  graph (like Unreal's RDG, AMD's Render Pipeline Shaders, or Filament's
  FrameGraph) should:

    a) Automatically derive VkImageMemoryBarrier / VkBufferMemoryBarrier
       from pass declarations — eliminating the entire class of missing-
       barrier GPU bugs.

    b) Track resource lifetimes — automatically allocate transient
       textures, recycle them across frames, and free them when no longer
       referenced.

    c) Support pass culling — if a pass's output is not consumed (e.g.,
       a track is muted), skip the pass entirely.

    d) Support async compute overlap — identify passes that can run on the
       async compute queue while graphics work proceeds in parallel.

  This is the single most impactful architectural change for both
  correctness and performance. It eliminates the global transfer→compute
  barrier hack, prevents the "stale GPU handle" crash class, and enables
  async compute overlap.

── 3.2  GPU RESOURCE STREAMING (VIRTUAL TEXTURING / TILED RESOURCES) ─────

  For projects with many high-resolution source clips, loading all frames
  into VRAM is impossible. Professional NLEs use:

    a) Sparse virtual textures — only the visible MIP levels of the
       currently displayed frames are resident in VRAM.

    b) Tiled resources (VK_EXT_image_drm_format_modifier or sparse
       binding) for 8K+ source material.

    c) Background streaming — prefetch ahead of the playhead, evict behind
       it, with a unified budget tied to available VRAM.

  The current PrefetchTexturePool (24 entries per shape) and
  GpuTextureCache (120 entries max) are fixed-size pools that don't adapt
  to project complexity. A streaming system would dynamically allocate
  budget based on what's visible.

── 3.3  MULTI-THREADED GPU COMMAND RECORDING ─────────────────────────────

  Currently, all GPU command recording for a frame happens on a single
  thread (FrameProducer). Vulkan supports multi-threaded command buffer
  recording via secondary command buffers and per-thread VkCommandPool.

  With a render graph, each pass could record its commands on a worker
  thread, then the primary command buffer calls vkCmdExecuteCommands.
  This would:
    - Reduce frame composition latency by 40-60% on multi-core systems
    - Allow effect chains to record in parallel with spine rendering
    - Enable better CPU utilization (Roundtable's Ryzen target)

── 3.4  PROPER COLOR MANAGEMENT (ACES / OCIO) ────────────────────────────

  The current color pipeline is sRGB-only with basic color correction
  effects. A professional NLE needs:

    a) OpenColorIO (OCIO v2) integration for color space transforms
    b) ACES (Academy Color Encoding System) workflow — scene-linear
       compositing with output display transforms
    c) HDR support (PQ/HLG) for HDR10/HLG export
    d) Color-managed viewer — show the correct colors for the target
       display, including HDR→SDR tone mapping for SDR monitors

  This is table stakes for any editor targeting professional use.

── 3.5  COLLABORATIVE / MULTI-USER PROJECT SUPPORT ──────────────────────

  Roundtable projects are single-user, single-file. Professional workflows
  require:

    a) Project locking — prevent two users from editing the same project
    b) Shared media storage with relative paths
    c) "Check out" individual sequences or bins
    d) Merge conflict resolution for project files

  This is a major architectural change (project format, file locking,
  network awareness) but essential for team workflows.

── 3.6  OFX / VST PLUGIN HOSTING ─────────────────────────────────────────

  Currently all effects are built-in GLSL compute shaders. A plugin
  architecture would allow:

    a) OFX (OpenFX) host for video effects — the industry standard used
       by DaVinci Resolve, Nuke, and HitFilm
    b) VST3 host for audio effects — EQ, compression, reverb, noise
       reduction
    c) A plugin SDK for third-party developers

  This is a major undertaking but dramatically expands the editor's
  capabilities.

── 3.7  NON-DESTRUCTIVE AUDIO EFFECTS & MIXING ───────────────────────────

  Currently only two audio effects exist: Fill Left with Right and
  Fill Right with Left. A professional editor needs:

    a) Parametric EQ (per-clip and per-track)
    b) Compressor/Limiter
    c) Noise gate / noise reduction
    d) Reverb and delay sends
    e) Track-level mixer with VU meters, solo, mute, pan, and submix
       busses
    f) Audio effects keyframing synchronized to the video timeline

── 3.8  ADVANCED TIMELINE FEATURES ───────────────────────────────────────

  Features that Premiere Pro and DaVinci Resolve users expect:

    a) Nested sequences with live editing (edit a nest, see it update in
       the parent timeline in real time)
    b) Multicam editing — sync multiple camera angles and cut between them
    c) Track targeting and patching (source patching for insert edits)
    d) Adjustment layers over clips (beyond the current track-level
       adjustment layer clip type)
    e) Track-level blending modes and opacity
    f) Markers with duration, color coding, and comments
    g) Time remapping with speed ramping (bezier curves on speed)

── 3.9  INTELLIGENT MEDIA MANAGEMENT ─────────────────────────────────────

    a) Proxy workflow — automatically generate low-res proxies for
       smooth editing, switch to full-res for export
    b) Media relinking — find moved/renamed files by content hash or
       filename search
    c) Consolidated project archiving — bundle all used media into a
       single portable folder
    d) Media verification — checksum-based integrity checking for
       archived projects

── 3.10 EXPORT PIPELINE OVERHAUL ─────────────────────────────────────────

    a) Background export with progress and ETA (currently blocks the UI
       in some paths)
    b) Export presets system (user-defined presets beyond hardcoded ones)
    c) Render-and-replace — render a complex section to a file, replace
       the timeline section with the rendered clip
    d) Queue multiple exports
    e) Direct upload to YouTube/Vimeo
    f) Smart rendering — only re-encode changed sections, copy untouched
       GOPs from source (requires codec-level GOP alignment)

── 3.11 SCRIPTING & AUTOMATION ───────────────────────────────────────────

    a) Python or Lua scripting API for automation
    b) Macro recording — record a sequence of actions and replay them
    c) Batch operations — apply effects/templates across multiple clips
    d) Expression-driven properties (e.g., "audio amplitude → scale")

── 3.12 SUBTITLE & CAPTION WORKFLOW ─────────────────────────────────────

    a) Native subtitle track type (not just imported SRT as text clips)
    b) Real-time caption preview during playback
    c) Style templates for captions
    d) Burn-in vs. soft subtitle export options
    e) Auto-transcription with speaker diarization

── 3.13 CROSS-PLATFORM SUPPORT ───────────────────────────────────────────

    Currently Windows-only. The codebase uses Vulkan (cross-platform),
    Qt 6 (cross-platform), and FFmpeg (cross-platform). The main blockers
    are:

    a) Windows-specific crash handler (MiniDumpWriteDump, SEH/VEH)
    b) WASAPI audio (PortAudio has CoreAudio/ALSA backends but may need
       tuning)
    c) DirectX interop paths
    d) Installer (Inno Setup is Windows-only; need .app bundle for macOS,
       AppImage/flatpak for Linux)

    Porting to at least macOS would significantly expand the user base.
    Linux support would enable render-farm deployments.

── 3.14 MACHINE LEARNING INTEGRATION ─────────────────────────────────────

    a) Scene detection (OmniShotCut harness exists but Python detector
       not redistributed)
    b) Auto-reframe for social media aspect ratios (plan exists in
       docs/REFRAME.txt)
    c) AI upscaling for low-res source material
    d) Smart background removal / rotoscoping (beyond chroma key)
    e) Speech-to-text with speaker identification
    f) Content-aware fill for gaps

── 3.15 PROFESSIONAL AUDIO WORKFLOW ──────────────────────────────────────

    a) Audio track types (mono, stereo, 5.1, ambisonics)
    b) Audio bus routing (sends, returns, submixes)
    c) Loudness monitoring (LUFS, true peak)
    d) Audio waveform display directly on timeline clips
    e) JKL shuttle with pitch-preserved speed change (already partially
       implemented)
    f) Audio transient detection for automatic beat-matching

── 3.16 ACCESSIBILITY ────────────────────────────────────────────────────

    a) Screen reader support (Qt Accessibility)
    b) High-contrast theme
    c) Keyboard-only operation mode
    d) Configurable UI scaling beyond the current UiScale system

================================================================================
FINAL REMARKS
================================================================================

  Roundtable is an impressive solo-developer NLE with a remarkably deep
  feature set: GPU-accelerated compositing, native Spine animation, Vulkan
  compute shaders, multi-track timeline editing, and AI-powered audio sync.
  The architecture is fundamentally sound: C++20, Vulkan compute, render
  graph direction, and command-pattern undo are all correct choices.

  The project's Achilles' heel is stability. The crash rate (540+ in one
  day) makes the editor unreliable for production work. Until the crash
  epidemic is solved, all feature work is secondary.

  The good news is that many of the fixes are well-understood and
  documented in repo memory — they "just" need implementation time.
  The paint recursion, GPU pipeline races, and use-after-free patterns
  all have clear resolution paths mapped out across dozens of analysis
  notes.

  The render graph migration (Phases A-C done) and GPU scheduler
  centralization are exactly the right long-term investments. Completing
  them (Phases D-F) and adding device-lost recovery would transform the
  editor from "powerful but unstable" to "production-ready."

  For the professional NLE vision, the three biggest differentiators
  would be: (1) proper color management via OCIO/ACES, (2) OFX plugin
  support, and (3) collaborative project workflows. These three features
  separate prosumer editors from professional ones.
