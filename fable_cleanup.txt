4.1  PER-STREAM COLOR MANAGEMENT          ** a)+b) DONE 2026-06-13; c) deferred **
     core/decode/ConvertDecodedFrame hardcoded SWS_CS_ITU709 + limited range
     for EVERY source.  So: SD / BT.601 content = wrong colors; BT.2020/HDR
     (PQ/HLG phone + camera footage, very common from yt-dlp) = wrong
     primaries, no tone-map; full-range JPEG/MJPEG = crushed levels.
       a) DONE — VideoDecoderInit reads color_space/range/trc/primaries and
          maps them to rt:: enums on VideoStreamInfo (colorMatrix/colorRange/
          colorTransfer/colorPrimaries; untagged stays Unspecified).  Also
          treats deprecated yuvj* pixel formats as full range.
       b) DONE — resolveColorConversion (decode/ColorConversion.cpp, FFmpeg-
          free, unit-tested in tests/core/test_color_conversion.cpp) turns the
          tags into a single decision; untagged falls back to the SD(≤576)→601
          / HD→709 broadcast height heuristic.  ConvertDecodedFrame feeds it to
          sws_setColorspaceDetails per-source (matrix + src range).
          CRITICAL: the GPU convert shaders (nv12/yuv420p/p010/yuva444p12) STILL
          hardcode 709-limited-SDR; making the CPU path per-source alone would
          flicker (cache mixes CPU-601 + GPU-709 frames of the same clip).  So
          all three GPU convert sites — convertDecodedToCacheGpu (prefetch) and
          BOTH inline NV12/YUV420P fast-paths in MediaPoolDecode (urgent/scrub)
          — now gate on resolveColorConversion(info).isGpuShaderDefault and bail
          to the CPU sws path for any non-709-limited-SDR source.  A clip is
          thus uniformly GPU or CPU, never mixed.  Export inherits the fix (it
          reuses the preview decode path).
       c) TODO — HDR->SDR tone-map (zscale or a GPU shader) for PQ/HLG.  Until
          then BT.2020 PQ/HLG gets the correct YUV matrix via the CPU path but
          is NOT tone-mapped (looks dark/desaturated); resolveColorConversion
          already flags these via ColorConversion::isHdr.  Real fix likely
          rides on 4.2 (16-bit float pipeline) so tone-map has headroom.
     NB: applies doubly to export — a 10-bit HEVC master currently transits
     8-bit BGRA (see 4.2).
     GATE for this change: core suite (incl. new test_color_conversion) +
     a runtime smoke on real SD/601, full-range JPEG, and BT.2020 sources
     (GPU-eligibility is logged at open: 709-limited-SDR = debug "GPU-eligible",
     everything else = warn "CPU sws path").  Not yet runtime-verified.

4.3  VFR DETECTED BUT IGNORED             ** a) DONE 2026-06-13; b) DEFERRED **
     VideoDecoderInit sets m_info.isVFR (also copied to MediaSourceService::
     isVariableFrameRate) and it was read NOWHERE; frame lookup is constant-fps
     math (VideoFrameMapping::mapTickToSourceFrame).
       a) DONE — "VFR" badge + explanatory tooltip in the project bin Frame
          Rate column (ProjectBinSync.cpp) and an amber warning in
          InterpretFootageDialog (new isVFR ctor arg, wired from
          info->isVFR in ProjectBinUI).
       b) DEFERRED (intentionally, after code review).  CORRECTION to the
          original premise: there is NO cumulative A/V drift in this codebase.
          mapTickToSourceFrame's frame number is converted back to a TIME
          (targetTime = frameNumber/fps) and BOTH the preview and scrub decode
          paths seek by TIMESTAMP (decoder.seek(targetTime) then decode-forward
          until pts>=target — MediaPoolPrefetchDecode.cpp:85, MediaPoolDecode.cpp
          :167); video never uses index-based seekToFrame (that's audio-only).
          targetTime is a linear fn of the timeline tick recomputed every frame,
          and audio is time-based too, so both are anchored to source-TIME — no
          drift accumulates.  What VFR actually causes here is bounded ~±half-
          frame jitter in WHICH frame is picked (cache key/seek target is
          quantised to the average-fps grid while real frames are uneven):
          slightly irregular frame-stepping, not desync.  The PTS-index rewrite
          touches the ONE unified tick->frame mapping (preview AND export) — the
          single riskiest change in the plan — for an UNVERIFIED payoff.  Do it
          only if a concrete repro on a real VFR clip shows the jitter is
          objectionable; then tests-FIRST per the ground rules.
       c) Optional Premiere-style conform-to-CFR on import (core/convert
          infrastructure already exists).

4.7  PROXY WORKFLOW
     Resolution tiers downscale at decode time, but heavy codecs still pay
     full decode cost (the ProRes-at-1/2-res workaround is the symptom).
     Ingredients all exist: conversion encoders, the assets/converted
     convention, MediaPool handle indirection.  A ProxyManager that generates
     (half-res NVENC H.264 or DNxHR LB) and lets MediaPool transparently swap
     source paths per handle.  Lower priority than 4.6.

4.2  16-BIT FLOAT GPU PIPELINE            ** top quality gap; largest; last **
     CachedFrame is 8-bit BGRA end-to-end.  10-bit HEVC (P010), 12-bit ProRes
     4444, and banding-sensitive gradients are all quantized to 8-bit at
     convert, composited, then re-encoded.  Pragmatic path: extend
     Nv12Converter to output RGBA16F (the P010 + yuva444p12 converters already
     exist and throw away depth at the final step), composite in 16F, dither
     down only at the viewport/encoder boundary; the CPU/cache fallback stays
     8-bit (CachedFrame grows a 'depth' field beside its existing 'origin' /
     'tier').  Gates every pro-format ambition (ProRes RAW, DNxHR HQX, HDR
     delivery).

4.9  SMALLER PARITY NOTES (file under "later"):
     - Growing-file refresh (OBS recordings opened mid-write): unsupported.
     - Audio conform: windowed decode w/ 16s lookahead is fine for editing,
       but long-timeline random seeks rebuild windows; Premiere conforms once
       to a CFA.  Revisit only if audio scrub feels laggy on hour-long
       timelines.
     - Timecode: no start-TC offset / drop-frame display (broadcast only).
     - Field order / interlace handling: absent (fine unless old TV content).
     - Captions: burn-in + sidecar SRT export (SrtIO) only; embedded 608/708
       is Premiere-land you likely don't need.
